# LEGO Battles — ndsrecomp port

Static-lift configuration for [ndsrecomp](https://github.com/mstan/ndsrecomp).
Nothing here is hand-written: `game.toml` is authored from cartridge header
fields, and `config/` is regenerated by `tools/lb_ndsrecomp.py`.

```
python tools/lb_ndsrecomp.py --out port/config
```

## Why the modes are trustworthy

ndsrecomp needs ARM vs Thumb per entry point, and a wrong mode is a silently and
totally wrong lift. The sibling LSW2 generator had to **guess** it from byte
patterns because its corpus kept only addresses, and it labels that a heuristic.

This project does not guess. Every mode comes from `out/eur/corpus.tsv` and has
been cross-checked twice: `docs/74` showed the vtable low bit agrees with the
recorded mode, and `docs/80`/`docs/83` verified the entire call graph against it
by control flow rather than linear disassembly.

## Two defects the validator caught

Generating was not enough; the first output was checked against the section
table and against the ROM, and it was wrong in two ways.

* **6 ITCM functions** at `0x01FF8000` had no program config. ITCM is a real
  ARM9 section with its own load address and now gets its own file.
* **152 entry points at `0x0216A000`+** were being written into the ARM9 static
  program. That is the **overlay load page**: they are overlay-resident
  functions carried in the ARM9 corpus, and lifting them as static would place
  code at an address 91 different overlays share. They are routed out, and the
  overlay configs cover them.

Every config's entry points are now inside its own `[load_address, +size)`, no
duplicates, no mode outside `arm`/`thumb`, and all 91 overlay SHA-1s verify
against the extracted images.

## Known gaps, stated rather than filled

* **ARM7 `mainram`** at `0x027E0000`, 96,376 bytes (autoload entry 1). The
  corpus has no entry points there and `docs/83` found **40 calls into it that
  survive control flow**, so it is real code and a real hole. No config is
  emitted for it rather than an empty one.
* Nothing has been **lifted or run** yet. This is the configuration the lift
  consumes, not the lift.

## Display

`game.toml` sets `adaptive_widescreen = "bottom"`, which is unusual: SM64DS and
Prime Hunters widen the upper 3D viewport, but LEGO Battles is an RTS whose game
field is the **touch screen**. `bottom` is a value ndsrecomp actually accepts
(`NDS_ADAPTIVE_BOTTOM`), checked in its source rather than assumed.

Widening is safe because `docs/85` established the simulation never calls view
code, so field of view is **client-local** and a widescreen host stays in
lockstep with a Vanilla client. The `[vanilla]` profile pins the DS layout for
the Vanilla rendering mode.

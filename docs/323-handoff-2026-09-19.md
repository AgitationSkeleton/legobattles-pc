## The frame rate: exactly where the diagnosis stopped

**Established, and none of it needs repeating:**

* About one run in four drops to **17-19 fps** instead of 57-58. The entire
  difference is `emu_ticks` (49.6 ms/frame against 14.5); present, draw, upload
  and swap are identical.
* The cause is ARM9 **ITCM** falling back to the interpreter.
  `cache_absent_itcm` reads 1,325,489,342 / 420,308,538 / 106,179,731 /
  679,003,605 in four slow runs and **0** in every fast one.
  `cache_absent_itcm_pc` is `0x01FF80E8` every time.
* ITCM holds `func_01FF8000` (the IRQ dispatcher — it reads IME at
  `0x04000208`) and `func_01FF8068` (the Nitro thread scheduler, which enters
  with `msr cpsr_c, #0xD2`, IRQs masked). These are the hottest loops in the
  game.
* It is **not** a missing lift, a registration problem, a range problem or
  bank ordering: `[lb_itcm] MISS ... candidates=1 inactive=1` says the entry
  was matched and the validation gate refused it.
* The refusal is byte inequality, not provenance (`prov=1`).
* Only **three words of the 200** differ from the lifted image, and they hold
  different values on different runs (see the next section). Early readings of
  this as "two byte images" were wrong and are retracted in docs/322.
* It **predates all of the work above**: `exp-fx1` read 19.60 fps at
  05:04 and `exp-fx4` 19.43 at 05:28, hours before the placement band code
  existed, and on a different route.

**The open question, precisely.** A full 0x320 dump at the moment of rejection
was captured (`screenshots/exp-predeploy2/stderr.log`) and it rules out the
reading this page first carried:

```
differing words: 3 of 200
  01FF8000  live E92D4067  expected E92D4000
  01FF80FC  live FF000000  expected EA000000
  01FF8100  live E35000FF  expected E3500001
```

Three words, and `01FF8000` read **E92D401B** in the previous slow run against
**E92D4067** in this one — different values at the same address on different
runs. So it is NOT a second static image and there is nothing to lift as a
variant; docs/322 retracts that in place.

As bytes the damage is at offsets 0x00, 0xFF and 0x100 — the last two
adjacent, a two-byte `FF FF` straddling a 256-byte boundary. `FF000000` is not
a valid ARM instruction. The gate is behaving correctly and refusing bytes that
are damaged, not different.

**Next step, in order:**

1. Read `0x01FF8000`, `0x01FF80FC`, `0x01FF8100` through the debug server's
   `read_mem`, which is a different path from the `bus_read_u32` that both the
   gate and the dump use. If it disagrees, the port's ITCM READ path is the
   bug and no writer needs chasing. Two instruments that share a path agreeing
   is not corroboration.
2. Only if the read path checks out, find the writer: `LB_WATCH` over
   `1FF8000:1FF8320` — but verify the watch fires at all first, because one
   run with it produced no lines whatsoever and that silence has not been
   explained.

**What was tried and did not answer it:** a `LB_WATCH=1FF8000:1FF8320`
watchpoint run produced no `[lb_watch]` lines at all, so either nothing wrote
ITCM in that run (it was a fast one) or the watch does not cover that range.
**Check the watch itself before trusting that silence** — this project's own
notes record a blank readout being a question, and a known-broken instrument
being a prerequisite rather than a lower priority.

**The instrument is built and deployed** and has already done its job once: on
the first ITCM rejection it prints `[lb_itcmdump]`, the whole 0x320-byte live
section, 4 words a line. `screenshots/exp-predeploy2/stderr.log` holds one.

Catching it is the only awkward part — roughly one run in four, and
`--build-flow` exits 1 without writing `fps.txt` when placement is not entered
(about half the time), which cost 5 of 6 runs in one A/B. A route that always
completes is worth more here than a faster one.

## Logging

Off unless asked for: `LB_FPLOG`, `LB_ENTLOG`, `LB_BANDLOG`, `LB_HUDLOG`,
`LB_SCANLOG`, `LB_TOUCHLOG`, `LB_WATCH`.

`LB_SCANLOG` is new and matters: `[lb_seen]`, `[lb_seam]`,
`[lb_bg2set]`, `[lb_anchor]`, `[lb_rows]` and the fog-model candidate dump were
firing on `g_scan_frames % 120` with **no flag at all**, so the shipped game
wrote them to stderr every two seconds and built their strings on the render
path. Now gated. Measured effect on the log: 360 KB to 168 KB on the same
route.

Always on, and each an increment or two on a path already being taken:
`cache_absent_itcm`, `g_declines`/`g_edge_declines`, `g_fp_served`,
`g_fp_saves`/`g_fp_restores`/`g_fp_abandoned`. The `[lb_itcm]` and
`[lb_itcmdump]` prints are one-shot per session and only fire after a dispatch
lookup has already failed.

Frame rate with all of it in place: **57-58 fps** on the standard route, which
is where it was before.

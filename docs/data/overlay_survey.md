# The overlays, surveyed

Per-overlay rows: [`overlay_inventory.tsv`](overlay_inventory.tsv), regenerated by

```powershell
python tools\lb_ovsurvey.py
```

Every number below comes from the ROM's own overlay table, the ARM9 RTTI, and a
byte-exhaustive classification of all 91 overlay images. Nothing is inherited
from the third-party decomp.

## The headline

| | |
| --- | ---: |
| overlays | **91** (`ov000`–`ov090`) |
| bytes in RAM, decompressed | **94,048** |
| bytes in ROM | 76,492 (78 of 91 BLZ-compressed, 13 stored) |
| **code** | **82,970 — 88.2 %** |
| data (literal pools, switch tables, static-init arrays) | 9,362 — 10.0 % |
| tail padding | 1,416 — 1.5 % |
| unclassified | **300 — 0.3 %** |
| function entry points | 372 (4.09 per overlay) |
| call sites into the ARM9 | 6,518, to 96 distinct functions |
| objective instances constructed | 903 |
| ASCII strings | **7 in 94 KB** — effectively none |

The six byte buckets sum to `ram_size` for every overlay; that is asserted in
the tool, not eyeballed.

**Against the ARM9.** The corpus README's denominator is 6,838 real functions /
**1,012,921 bytes**. Overlay *code* is **82,970 bytes = 8.2 %** of that; the
whole overlay image, data included, is 9.3 %. The overlays are a tenth of the
game's code, not a hidden half of it.

**The "~268 KB of overlays" figure this survey was commissioned against is
wrong** by a factor of nearly three. The images total 94,048 bytes decompressed
and 76,492 in the ROM. Where 268 KB came from was not established; it is not the
sum of the files, of `ram_size`, of `rom_size`, or of the two together.

## They are genuinely swapped, and they all share one address

Read from the ROM's overlay table — `out/eur/overlays/overlay_table.bin`, 2,912
bytes = 91 × 32-byte entries, mirrored in `header.json` — not assumed:

* **every** entry's `ram_address` is `0x0216A2E0`. All 91. Not a range, one address.
* every entry's `bss_size` is `0x20`.
* file IDs are 0–90, contiguous, one per overlay.
* `static_init` is non-empty for all 91 and always sits at the very tail of the image.

`0x0216A2E0` is exactly the ARM9 module parameters' `static_bss_end`. The
overlay slot begins at the first byte past the ARM9's `.bss`. The largest
overlay is `ov047` at 6,432 bytes, so the slot spans `0x0216A2E0`–`0x0216BC00`
and **exactly one overlay can be resident at a time**. There are 47 distinct end
addresses among the 91.

This is why an address in overlay space is meaningless without naming the
overlay — see the hazard at the end of this page.

## Every one of them is a mission event script

All 91 have the same four-function skeleton:

```
+0x0000   ldr r3,[pc,#0]; bx r3        4-byte entry thunk
+0x0004   .word <handler>|1            its literal
+0x0008   the event handler            push {...}; switch on the event number
   ...
  tail    two static constructors      register the handler; construct the BSS object
  tail    .word[] static-init array    the ctor pointers the loader runs
```

The handler takes `(self, event)` and switches on a small integer. The
discriminants fall in **two bands**: a low one starting at 0 (`0` in 78 of the
91 overlays, `1` in 67, then 3, 5, 7, 9 … thinning out), and a contiguous high
band **`0x84`–`0x8C`** that **all 91** overlays use (`0x84` in 78, `0x85` in 49,
`0x86` in 34). The low band reads as per-mission trigger slots and the high band
as engine-raised lifecycle events, but no name has been attached to either.

Each arm is straight-line scripting: set team relationships, grant starting
bricks, construct objectives, arm timers, open a dialog. There is no interpreter
and no bytecode; the "script" is compiled Thumb.

Seven four-character ASCII runs in 94 KB is noise. The overlays address all text
by numeric ID into `LOC/*.lng`, so a `strings` pass over them returns nothing and
would have suggested, wrongly, that they are opaque data.

## Which overlay is which mission — complete, from the ROM

`Battles::CampaignMissionBase` subclasses carry a **`GetOverlayId()` at vtable
slot 11**, compiled to a two-instruction constant return:

```
020426A0  ldr r0,[pc,#0]    ; = 0x0000002F
020426A2  bx  lr                             -> ck1_1 is ov047
```

Scanning all 511 vtables in the ARM9 RTTI, **exactly 91** have a slot-11
constant return in 0–90, and their values are a **bijection onto 0–90**. No
value is claimed twice and none is missing.

* It **agrees with all 64** mappings previously known, which were recovered by a
  third party's Thumb emulator.
* It **closes the 26** that `docs/06` and `campaign_missions.tsv` left as `?` —
  the whole of `cw` and the rest of `pp`, which the emulator could not reach
  because those loaders are ARM. They are `ov065`–`ov090`.
* The objective text corroborates independently: `ov075` = `TheManorAct3` says
  *"Destroy the Imperial Manor"*; `ov072` = `SaveTheMatesAct3` says *"Free 3
  mates"*; `ov081` = `WitchesBrewAct1` says *"Protect and repair the
  Cauldron"*; `ov076` = `NoBonesAboutItAct1` says *"Collect 5 piles of
  bones"*.

**`ov000` is `Battles::CampaignBase`** — the base class, the 91st slot-11
claimant, returning 0. It has no `.map`, opens no mission dialog, and constructs
**11 of the 13 objective types exactly once each**. That shape is a template or
reference implementation, not a playable mission. This answers the open question
`docs/06` and the `docs/10` roadmap both record as "what `ov000` is".

## Correcting the premise: the ARM9 is not bypassed

"Mission logic mostly is not in the ARM9" is about half right, and the half that
is wrong matters.

* Each of the 90 missions **also has an ARM9 class**. Vtables occupy
  `0x02144F10`–`0x02147BEC`; the per-mission virtuals live in
  `0x0203EF30`–`0x02045038`. That band holds **700 corpus functions / 25,944
  bytes**. The `.map` filename and the mission's string IDs are in ARM9 rodata,
  not in the overlay.
* The scripting vocabulary the overlays call lives at `0x02045100`–`0x0204B000`:
  **390 functions / 23,496 bytes**.
* No campaign vtable slot points into overlay space — checked, 0 of 90. The
  traffic is one-way: overlays call the ARM9, the ARM9 reaches the overlay only
  through the handler the static constructor registers.

So the ARM9 holds the engine, the objective classes, the scripting macros *and*
a per-mission class; the overlay holds only that mission's compiled event
script. ~49 KB of ARM9 mission machinery against ~83 KB of overlay script.

## They were not an unexamined blind spot — but one figure was open

The overlays are deliberately absent from `arm9_inventory.tsv` (0 rows in
overlay space) and from the 1,012,921-byte denominator. That exclusion is
correct, not an oversight: they are a different address space.

Prior work already covers them: `tools/lb_overlays.py`, `docs/06`, `docs/82`,
`overlay_corpus.tsv`, `overlay_coverage.tsv`, `mission_api.tsv`,
`mission_objectives.tsv`, and the recompiler lift in `docs/90`.

What *was* open is an item `docs/10` lists in its own open-questions table:

> the overlays' 93.9% denominator includes each overlay's literal pools and
> data, as the ARM7's did — separate code from data before chasing the last 6%

That is what this survey closes: **88.2 % code, 10.0 % data, 1.5 % padding,
0.3 % unaccounted.** The old 93.9 % was merged function *extents*, which
swallow the literal pools and switch tables sitting inside them.

### Why the walk used to stop early

`lb_scan.walk` implements the **ARM** PC-relative switch idiom
(`addls pc, pc, rN, lsl #2`) only. Every overlay dispatches its events with the
**Thumb** halfword-table idiom:

```
adds r0, r4, r4 ; add r0, pc ; ldrh r0,[r0,#6] ; lsls/asrs ; add pc, r0
<halfword table of signed offsets>
```

Without it the walk reaches the dispatch and stops: measured **56.0 %** of
overlay bytes as code. With it, **88.2 %**.

One trap inside that: the table length must **not** be taken from the preceding
`cmp`. The compared register is usually not the index register — `ov028` is
`cmp r4,#5` then `adds r0,r4,r4` — so a `cmp` lookup keyed on the index register
finds nothing and the switch is skipped silently. The table is instead
self-limiting: every arm lies after the table, so the table cannot extend past
the lowest target seen.

## A hazard: `corpus.tsv` conflates all 91 overlays

`out/eur/corpus.tsv` contains **152 rows at overlay addresses**, each attributed
to whichever overlay happened to be scanned into that slot. Because all 91 share
`0x0216A2E0`, a name looked up there is wrong for roughly 98 % of overlays —
`0x0216A2E8` resolves to `func_ov090_0216a2e8` for every overlay's handler,
including `ov000`'s.

`arm9_inventory.tsv` is clean: **0 rows** in overlay space. Any tool that reads
`corpus.tsv` for an overlay-space address should be passed the overlay id and
resolve against `overlay_corpus.tsv` instead.

## What this survey did not establish

1. **The 300 unclassified bytes** (2–4 per overlay, only 4 of them zero) are
   almost certainly alignment filler between a function end and the next
   4-aligned literal pool. They are unreached and non-zero; that is all that is
   proven.
2. **Eight `.map` assignments remain uncorroborated** — the `map_corroborated`
   column carries `NO`, inherited from `campaign_missions.tsv`. Slot 11 gives
   *class → overlay* with certainty; for those eight it is the *class → map*
   link that is weak, and this survey does not strengthen it.

   There is, however, a route not taken here. Each overlay's
   `OpenMissionDialog` ids land in **one contiguous `LOC` block**, laid out as
   *title, description, briefing, then objectives, three IDs per line*:
   `ov078` uses 1648/1651/1654, under title 1644 "Convenient Alliance";
   `ov080` uses 1661–1727, under title 1657 "Strength in Numbers". Since the
   blocks run in presentation order, the block index pins each overlay's
   position in its act. **Do not read the class names as titles** — `ov047` is
   `CampaignMission1_RepairTheGarrisonAct1` and the game calls it "Dark
   Shadows" — which is exactly the mistake that makes `cw2_1`/`cw2_2` look
   swapped when it is not evidence of anything.
3. **`ov000`'s runtime role.** Its class is `CampaignBase`; the call site that
   loads overlay 0 was not found, so whether it backs `test1.map`, a default
   path, or nothing at all is undetermined.
4. **Skirmish and multiplayer are unaccounted for.** `Maps/` holds 30 `mp*`
   maps, and `Battles::MultiplayerMissionBase` has **no** slot-11 overlay id. No
   overlay serves them; presumably that scripting is wholly in the ARM9, but
   that was not checked.
5. **21 of the 96 API targets** are called by exactly one overlay each and
   remain unnamed.
6. **The event numbers are not decoded.** The two discriminant bands are the
   campaign's event vocabulary and no name has been attached to any value in
   either.
